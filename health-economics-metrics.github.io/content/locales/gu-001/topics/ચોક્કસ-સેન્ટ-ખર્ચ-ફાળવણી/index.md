# ચોક્કસ-સેન્ટ ખર્ચ ફાળવણી

નાણાંની કુલ રકમ — વહેંચાયેલ અનુદાન, માળખાકીય બિલ, બજેટ-અસર આંકડો — ને ઘણા પ્રાપ્તકર્તાઓમાં ભોળા ટકાવારી અંકગણિતથી વહેંચવાથી નિયમિતપણે એવા ભાગો મળે છે જે મૂળ કુલમાં પાછા સરવાળે થતા નથી. ચોક્કસ-સેન્ટ ફાળવણી તેનો ઉકેલ છે: ન્યૂનતમ ચલણ એકમો (સેન્ટ)માં કામ કરતી પૂર્ણાંક/દશાંશ પદ્ધતિ, જે ખાતરી આપે છે કે ભાગો *બરાબર* સમગ્ર જેટલા થાય, ભલે તે ગમે તેટલું અસમાન વહેંચાય. કોઈપણ સૉફ્ટવેર એન્જિનિયર જેને વહેંચાયેલા કુલને સેન્ટ સુધી મેળ ખવડાવવો પડે — પગારપત્રક, અનુદાન વિતરણ, વહેંચાયેલ-સેવા ચાર્જબૅક — તેને આ પૅટર્ન જોઈએ, ફ્લોટિંગ-પૉઇન્ટ ટકાવારી નહીં.

## આ શા માટે મહત્ત્વનું છે

આ એન્ટરપ્રાઇઝ સૉફ્ટવેર એન્જિનિયરિંગમાં નામાંકિત, પાયાની પૅટર્ન છે: Martin Fowler ના *Patterns of Enterprise Application Architecture* (2002) માં `Money` અને `Allocate` દસ્તાવેજીકૃત છે ચોક્કસ એટલા માટે કે "$100 ને ત્રણ રીતે વહેંચો" એવી સમસ્યા છે જે ભોળો કોડ સતત ખોટી કરે છે, અને શાંતિથી ખોટી કરે છે — ભૂલ ત્યારે જ સપાટી પર આવે છે જ્યારે કોઈ ચોપડા મેળવે છે અને ભાગો કુલથી એક સેન્ટ ઓછા (કે વધુ) જુએ છે. આરોગ્ય-અર્થશાસ્ત્ર અને NHS નાણા કામમાં આ શૈક્ષણિક નથી: બજેટ-અસર કુલ સાઇટ્સ, વર્ષો કે નિર્દેશાલયોમાં વહેંચાય છે; વહેંચાયેલ માળખાકીય અને લાઇસન્સ ખર્ચ હેડકાઉન્ટ કે પ્રવૃત્તિ હિસ્સા દ્વારા વિભાગોમાં ફાળવાય છે. આમાંનો દરેક વિભાજન બરાબર મેળ ખાવો જોઈએ, કારણ કે જે નાણા નિર્દેશકને કુલ સાથે સરવાળે ન થતા ભાગો અપાય તે સમગ્ર મૉડેલ પરનો વિશ્વાસ ગુમાવે છે.

## ગણિત

```
Naive (broken) method:
  part_i = round(total × share_i / Σ shares)     — rounds each part independently

Exact method (largest remainder / "largest remainder allocation"):
  1. base_i = floor(total_minor_units × share_i / Σ shares)   — whole minor units (cents) only
  2. remainder = total_minor_units − Σ base_i                  — leftover cents, always < number of recipients
  3. distribute 1 extra minor unit each to the `remainder` recipients with the
     largest fractional remainder from step 1, until the leftover is exhausted

Result: Σ part_i == total, always, by construction.
```

ચોક્કસ પદ્ધતિ ક્યારેય કોઈ ભાગને અલગ ગોળ કરતી નથી — તે *આખી ફાળવણી*ને એક ક્રિયા તરીકે ગોળ કરે છે, જે સરવાળા અચળને ટકાવે છે.

## ઉકેલેલું ઉદાહરણ

$100.00 ને ત્રણ સમાન રીતે વહેંચો (`shares = [1, 1, 1]`).

ભોળી પદ્ધતિ: $100.00 ÷ 3 = $33.333…, અલગ-અલગ નજીકના સેન્ટ સુધી ગોળ કરતાં દરેક પ્રાપ્તકર્તા માટે $33.33. સરવાળો: $33.33 × 3 = $99.99 — એક સેન્ટ ગાયબ થઈ ગયો, અને કોઈ એક લાઇન આઇટમ નિરીક્ષણથી પકડાય તેટલી "ખોટી" નથી.

ચોક્કસ પદ્ધતિ: ત્રણેય માટે `base` = $33.33 (`floor(10,000 / 3) = 3,333` સેન્ટ દરેક, કુલ 9,999 ન્યૂનતમ એકમો), 1 સેન્ટ બાકી (10,000 − 9,999). તે એકમાત્ર બાકી સેન્ટ ભાગાકારમાં સૌથી મોટો અપૂર્ણાંક બાકી ધરાવતા પ્રાપ્તકર્તાને જાય છે — ચોક્કસ પ્રાપ્તકર્તા આંતરિક ટાઇ-બ્રેક વિગત છે, જેના પર કૉલરે નિર્ભર ન થવું જોઈએ. બે પ્રાપ્તકર્તાને $33.33 અને એકને $33.34 મળે છે, અને ત્રણેય ભાગોનો સરવાળો બરાબર $100.00 થાય છે.

[બજેટ અસર વિશ્લેષણ](../બજેટ-અસર-વિશ્લેષણ/) ને જ્યારે પણ કુલ બજેટ-અસર આંકડો સાઇટ્સ, કોહોર્ટ્સ કે નાણાકીય વર્ષોમાં વહેંચવો અને પ્રકાશિત કુલ સાથે મેળવવો પડે ત્યારે બરાબર આ અંકગણિત જોઈએ — ડ્રિફ્ટ વિના આવી ઘણી લાઇન આઇટમ્સના સરવાળાની સાથી સમસ્યા માટે [ચલણ-સુરક્ષિત ખર્ચ રોલઅપ](../ચલણ-સુરક્ષિત-ખર્ચ-રોલઅપ/) જુઓ.

## સૉફ્ટવેર એન્જિનિયરિંગ સાથે સંબંધ

આ શાબ્દિક રીતે એન્ટરપ્રાઇઝ સૉફ્ટવેર આર્કિટેક્ચરની "Money પૅટર્ન" છે — બરાબર આ બગ વર્ગ માટે પાયાની, નામાંકિત પૅટર્ન, એકલ યુક્તિ નહીં. વાસ્તવિક નાણાકીય-મેળવણી નિષ્ફળતાઓ બરાબર આ બગ વર્ગમાંથી મોકલાઈ છે: `f64` માં ગણેલા ટકાવારી વિભાજન, પ્રાપ્તકર્તા દીઠ ગોળ, અને મૂળ કુલ સામે ક્યારેય ન તપાસાયેલા. તે આ રિપોઝિટરીના [માલિકીનો કુલ ખર્ચ](../માલિકીનો-કુલ-ખર્ચ/) મૉડ્યુલ સાથે સીધું જોડાય છે, જે હાલમાં વર્ષો અને વિકલ્પોમાં સાદા ફ્લોટિંગ-પૉઇન્ટ ખર્ચનો સરવાળો કરે છે — જ્યારે પણ TCO કે બજેટ-અસર કુલ ફક્ત સરવાળે નહીં પણ ફાળવવો હોય ત્યારે એ જ ચોક્કસતા શિસ્ત લાગુ પડે છે.

## સામાન્ય ભૂલો

- **સૌથી-મોટા-બાકીને બદલે ટકાવારી-પછી-ગોળ**: ફ્લોટિંગ-પૉઇન્ટ ટકાવારીથી ફાળવવું અને દરેક પ્રાપ્તકર્તાને અલગ ગોળ કરવું, જે ગોળાઈ ભૂલ વધારે છે અને ખાસ કરીને ઘણા પ્રાપ્તકર્તાઓમાં ભાગ્યે જ કુલ સુધી સરવાળે થાય છે.
- **ચલણ લઘુતમ-એકમ ઘાતાંકોની અવગણના**: દરેક ચલણમાં 2 દશાંશ સ્થાનો છે એમ માનવું — જાપાની યેનમાં 0 છે, કેટલાક ચલણોમાં 3 — હાથથી લખેલું ટકાવારી વિભાજન સામાન્ય રીતે 2 હાર્ડ-કોડ કરે છે અને અન્ય ચલણો માટે શાંતિથી તૂટે છે; ચોક્કસ-ફાળવણી રૂટિન ઘાતાંક ચલણમાંથી જ વાંચે છે (ISO 4217).
- **પહેલેથી ફાળવાયેલા બાકીની ફરી ફાળવણી**: અગાઉની ફાળવણીમાંથી જે બાકી રહ્યું તેના પર ફરી ફાળવણી રૂટિન ચલાવવું, idempotency તપાસ વિના, જે એ જ પ્રાપ્તકર્તાને એ જ સેન્ટ બે વાર જમા કરી શકે.

## સ્રોતો

- Fowler M. "Patterns of Enterprise Application Architecture." Addison-Wesley, 2002 — the `Money` and `Allocate` patterns.
- ISO 4217 — currency and funds code standard, which defines each currency's minor-unit exponent.
