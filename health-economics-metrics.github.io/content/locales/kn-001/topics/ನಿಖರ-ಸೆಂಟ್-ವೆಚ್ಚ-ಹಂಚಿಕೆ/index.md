# ನಿಖರ-ಸೆಂಟ್ ವೆಚ್ಚ ಹಂಚಿಕೆ

ಹಣದ ಒಟ್ಟು ಮೊತ್ತವನ್ನು — ಹಂಚಿಕೆಯ ಅನುದಾನ, ಮೂಲಸೌಕರ್ಯ ಬಿಲ್, ಬಜೆಟ್-ಪ್ರಭಾವ ಅಂಕಿ — ಹಲವು ಸ್ವೀಕರಿಸುವವರ ನಡುವೆ ಸರಳ ಶೇಕಡಾ ಅಂಕಗಣಿತದಿಂದ ವಿಭಜಿಸುವುದು ನಿಯಮಿತವಾಗಿ ಮೂಲ ಒಟ್ಟಿಗೆ ಮರಳಿ ಕೂಡದ ಭಾಗಗಳನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ. ನಿಖರ-ಸೆಂಟ್ ಹಂಚಿಕೆ ಪರಿಹಾರ: ಕಿರು ಕರೆನ್ಸಿ ಘಟಕಗಳಲ್ಲಿ (ಸೆಂಟ್‌ಗಳು) ಕೆಲಸ ಮಾಡುವ ಪೂರ್ಣಾಂಕ/ದಶಮಾಂಶ ವಿಧಾನ, ಅದು ಎಷ್ಟೇ ಅಸಮವಾಗಿ ಭಾಗವಾದರೂ ಭಾಗಗಳು *ನಿಖರವಾಗಿ* ಒಟ್ಟಿಗೆ ಕೂಡುವುದನ್ನು ಖಾತರಿಪಡಿಸುತ್ತದೆ. ವಿಭಜಿಸಿದ ಒಟ್ಟನ್ನು ಸೆಂಟ್‌ಗೆ ಹೊಂದಿಸಬೇಕಾದ ಯಾವುದೇ ಸಾಫ್ಟ್‌ವೇರ್ ಎಂಜಿನಿಯರ್ — ವೇತನ, ಅನುದಾನ ವಿತರಣೆ, ಹಂಚಿಕೆಯ-ಸೇವೆ ಮರುಪಾವತಿ — ಫ್ಲೋಟಿಂಗ್-ಪಾಯಿಂಟ್ ಶೇಕಡಾಗಳಲ್ಲ, ಈ ಮಾದರಿಯನ್ನು ಬಯಸುತ್ತಾನೆ.

## ಇದು ಏಕೆ ಮುಖ್ಯ

ಇದು ಉದ್ಯಮ ಸಾಫ್ಟ್‌ವೇರ್ ಎಂಜಿನಿಯರಿಂಗ್‌ನ ಹೆಸರಿಸಿದ, ಮೂಲಭೂತ ಮಾದರಿ: Martin Fowlerನ *Patterns of Enterprise Application Architecture* (2002) `Money` ಮತ್ತು `Allocate` ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ, ಏಕೆಂದರೆ "$100 ಅನ್ನು ಮೂರು ರೀತಿ ವಿಭಜಿಸು" ಎಂಬುದು ಸರಳ ಕೋಡ್ ನಿರಂತರವಾಗಿ ತಪ್ಪಾಗಿ ಮಾಡುವ ಸಮಸ್ಯೆ, ಮತ್ತು ಮೌನವಾಗಿ ತಪ್ಪುತ್ತದೆ — ಯಾರಾದರೂ ಪುಸ್ತಕಗಳನ್ನು ಹೊಂದಿಸಿ ಭಾಗಗಳು ಒಟ್ಟಿಗಿಂತ ಒಂದು ಸೆಂಟ್ ಕಡಿಮೆ (ಅಥವಾ ಹೆಚ್ಚು) ಎಂದು ಕಂಡುಕೊಂಡಾಗ ಮಾತ್ರ ದೋಷ ಮೇಲ್ಮೈಗೆ ಬರುತ್ತದೆ. ಆರೋಗ್ಯ-ಅರ್ಥಶಾಸ್ತ್ರ ಮತ್ತು NHS ಹಣಕಾಸು ಕೆಲಸದಲ್ಲಿ ಇದು ಶೈಕ್ಷಣಿಕವಲ್ಲ: ಬಜೆಟ್-ಪ್ರಭಾವ ಒಟ್ಟುಗಳನ್ನು ಸ್ಥಳಗಳು, ವರ್ಷಗಳು ಅಥವಾ ನಿರ್ದೇಶನಾಲಯಗಳಾದ್ಯಂತ ವಿಭಜಿಸಲಾಗುತ್ತದೆ; ಹಂಚಿಕೆಯ ಮೂಲಸೌಕರ್ಯ ಮತ್ತು ಪರವಾನಗಿ ವೆಚ್ಚಗಳನ್ನು ತಲೆಗಣತಿ ಅಥವಾ ಚಟುವಟಿಕೆ ಪಾಲಿನ ಮೂಲಕ ವಿಭಾಗಗಳಾದ್ಯಂತ ಹಂಚಲಾಗುತ್ತದೆ. ಆ ಪ್ರತಿ ವಿಭಜನೆಯೂ ನಿಖರವಾಗಿ ಹೊಂದಿಕೆಯಾಗಬೇಕು, ಏಕೆಂದರೆ ಒಟ್ಟಿಗೆ ಕೂಡದ ಭಾಗಗಳನ್ನು ಪಡೆದ ಹಣಕಾಸು ನಿರ್ದೇಶಕ ಇಡೀ ಮಾದರಿಯ ಮೇಲೆ ನಂಬಿಕೆ ಕಳೆದುಕೊಳ್ಳುತ್ತಾನೆ.

## ಗಣಿತ

```
Naive (broken) method:
  part_i = round(total × share_i / Σ shares)     — rounds each part independently

Exact method (largest remainder / "largest remainder allocation"):
  1. base_i = floor(total_minor_units × share_i / Σ shares)   — whole minor units (cents) only
  2. remainder = total_minor_units − Σ base_i                  — leftover cents, always < number of recipients
  3. distribute 1 extra minor unit each to the `remainder` recipients with the
     largest fractional remainder from step 1, until the leftover is exhausted

Result: Σ part_i == total, always, by construction.
```

ನಿಖರ ವಿಧಾನ ಯಾವ ಭಾಗವನ್ನೂ ಪ್ರತ್ಯೇಕವಾಗಿ ದುಂಡಾಗಿಸುವುದಿಲ್ಲ — *ಇಡೀ ಹಂಚಿಕೆಯನ್ನು* ಒಂದೇ ಕಾರ್ಯಾಚರಣೆಯಾಗಿ ದುಂಡಾಗಿಸುತ್ತದೆ, ಇದು ಮೊತ್ತದ ಅಚರತೆಯನ್ನು ಉಳಿಸುತ್ತದೆ.

## ಬಿಡಿಸಿದ ಉದಾಹರಣೆ

$100.00 ಅನ್ನು ಮೂರು ಸಮ ರೀತಿ ವಿಭಜಿಸಿ (`shares = [1, 1, 1]`).

ಸರಳ ವಿಧಾನ: $100.00 ÷ 3 = $33.333…, ಪ್ರತ್ಯೇಕವಾಗಿ ಹತ್ತಿರದ ಸೆಂಟ್‌ಗೆ ದುಂಡಾಗಿಸಿದರೆ ಪ್ರತಿ ಸ್ವೀಕರಿಸುವವರಿಗೆ $33.33. ಕೂಡಿಸಿದರೆ: $33.33 × 3 = $99.99 — ಒಂದು ಸೆಂಟ್ ಕಣ್ಮರೆಯಾಗಿದೆ, ಮತ್ತು ಯಾವ ಒಂದು ಸಾಲು ಅಂಶವೂ ಪರಿಶೀಲನೆಯಲ್ಲಿ ಗುರುತಿಸುವಷ್ಟು "ತಪ್ಪಲ್ಲ".

ನಿಖರ ವಿಧಾನ: ಮೂವರಿಗೂ `base` = $33.33 (`floor(10,000 / 3) = 3,333` ಸೆಂಟ್‌ಗಳಂತೆ ಒಟ್ಟು 9,999 ಕಿರು ಘಟಕಗಳು), 1 ಸೆಂಟ್ ಶೇಷ ಉಳಿಯುತ್ತದೆ (10,000 − 9,999). ಆ ಒಂದು ಉಳಿದ ಸೆಂಟ್ ಭಾಗಾಕಾರದಲ್ಲಿ ಅತಿ ದೊಡ್ಡ ಭಿನ್ನರಾಶಿ ಶೇಷ ಇರುವ ಸ್ವೀಕರಿಸುವವರಿಗೆ ಹೋಗುತ್ತದೆ — ನಿರ್ದಿಷ್ಟ ಸ್ವೀಕರಿಸುವವರು ಆಂತರಿಕ ಟೈ-ಬ್ರೇಕ್ ವಿವರ, ಕರೆ ಮಾಡುವವರು ಅವಲಂಬಿಸಬೇಕಾದದ್ದಲ್ಲ. ಇಬ್ಬರಿಗೆ $33.33 ಮತ್ತು ಒಬ್ಬರಿಗೆ $33.34 ಸಿಗುತ್ತದೆ, ಮತ್ತು ಮೂರು ಭಾಗಗಳು ನಿಖರವಾಗಿ $100.00 ಕೂಡುತ್ತವೆ.

ಒಟ್ಟು ಬಜೆಟ್-ಪ್ರಭಾವ ಅಂಕಿಯನ್ನು ಸ್ಥಳಗಳು, ಸಮೂಹಗಳು ಅಥವಾ ಹಣಕಾಸು ವರ್ಷಗಳಾದ್ಯಂತ ವಿಭಜಿಸಿ ಪ್ರಕಟಿತ ಒಟ್ಟಿಗೆ ಹೊಂದಿಸಬೇಕಾದಾಗೆಲ್ಲ [ಬಜೆಟ್-ಪ್ರಭಾವ ವಿಶ್ಲೇಷಣೆ](../ಬಜೆಟ್-ಪರಿಣಾಮ-ವಿಶ್ಲೇಷಣೆ/)ಗೆ ಬೇಕಾದ ಅಂಕಗಣಿತ ಇದೇ — ಅಂತಹ ಅನೇಕ ಸಾಲು ಅಂಶಗಳನ್ನು ಚಲನೆಯಿಲ್ಲದೆ ಕೂಡಿಸುವ ಸಹವರ್ತಿ ಸಮಸ್ಯೆಗೆ [ಕರೆನ್ಸಿ-ಸುರಕ್ಷಿತ ವೆಚ್ಚ ಸಂಕಲನ](../ಕರೆನ್ಸಿ-ಸುರಕ್ಷಿತ-ವೆಚ್ಚ-ಸಂಕಲನ/) ನೋಡಿ.

## ಸಾಫ್ಟ್‌ವೇರ್ ಎಂಜಿನಿಯರಿಂಗ್‌ನೊಂದಿಗಿನ ಸಂಬಂಧ

ಇದು ಅಕ್ಷರಶಃ ಉದ್ಯಮ ಸಾಫ್ಟ್‌ವೇರ್ ವಾಸ್ತುಶಿಲ್ಪದ "Money ಮಾದರಿ" — ಇದೇ ದೋಷ ವರ್ಗಕ್ಕೆ ಹೆಸರಿಸಿದ, ಮೂಲಭೂತ ಮಾದರಿ, ಒಂದು ಬಾರಿಯ ತಂತ್ರವಲ್ಲ. ನಿಜವಾದ ಹಣಕಾಸು-ಹೊಂದಾಣಿಕೆ ವೈಫಲ್ಯಗಳು ಇದೇ ವರ್ಗದ ದೋಷದಿಂದ ಹೊರಬಂದಿವೆ: `f64`ನಲ್ಲಿ ಲೆಕ್ಕ ಹಾಕಿದ ಶೇಕಡಾ ವಿಭಜನೆಗಳು, ಪ್ರತಿ ಸ್ವೀಕರಿಸುವವರಿಗೆ ದುಂಡಾಗಿಸಿದ್ದು, ಮತ್ತು ಮೂಲ ಒಟ್ಟಿನ ವಿರುದ್ಧ ಎಂದಿಗೂ ಪರಿಶೀಲಿಸದೆ. ಇದು ಈ ರೆಪೊಸಿಟರಿಯ [ಒಟ್ಟು ಮಾಲೀಕತ್ವ ವೆಚ್ಚ](../ಒಟ್ಟು-ಮಾಲೀಕತ್ವ-ವೆಚ್ಚ/) ಘಟಕಕ್ಕೆ ನೇರವಾಗಿ ಸಂಪರ್ಕಿಸುತ್ತದೆ, ಅದು ಈಗ ವರ್ಷಗಳು ಮತ್ತು ಆಯ್ಕೆಗಳಾದ್ಯಂತ ಸಾದಾ ಫ್ಲೋಟಿಂಗ್-ಪಾಯಿಂಟ್ ವೆಚ್ಚಗಳನ್ನು ಕೂಡಿಸುತ್ತದೆ — TCO ಅಥವಾ ಬಜೆಟ್-ಪ್ರಭಾವ ಒಟ್ಟನ್ನು ಕೇವಲ ಕೂಡಿಸುವ ಬದಲು ಹಂಚಬೇಕಾದಾಗೆಲ್ಲ ಅದೇ ನಿಖರತೆ ಶಿಸ್ತು ಅನ್ವಯಿಸುತ್ತದೆ.

## ಎಡವಟ್ಟುಗಳು

- **ಅತಿ ದೊಡ್ಡ-ಶೇಷದ ಬದಲು ಶೇಕಡಾ-ನಂತರ-ದುಂಡಾಗಿಸುವಿಕೆ**: ಫ್ಲೋಟಿಂಗ್-ಪಾಯಿಂಟ್ ಶೇಕಡಾಗಳಿಂದ ಹಂಚಿ ಪ್ರತಿ ಸ್ವೀಕರಿಸುವವರನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ದುಂಡಾಗಿಸುವುದು, ಇದು ದುಂಡಾಗಿಸುವ ದೋಷವನ್ನು ಹೆಚ್ಚಿಸುತ್ತದೆ ಮತ್ತು ವಿಶೇಷವಾಗಿ ಅನೇಕ ಸ್ವೀಕರಿಸುವವರಲ್ಲಿ ಅಪರೂಪವಾಗಿ ಒಟ್ಟಿಗೆ ಕೂಡುತ್ತದೆ.
- **ಕರೆನ್ಸಿ ಕಿರು-ಘಟಕ ಘಾತಗಳ ನಿರ್ಲಕ್ಷ್ಯ**: ಪ್ರತಿ ಕರೆನ್ಸಿಗೆ 2 ದಶಮಾಂಶ ಸ್ಥಾನಗಳಿವೆ ಎಂದು ಊಹಿಸುವುದು — ಜಪಾನೀ ಯೆನ್‌ಗೆ 0, ಕೆಲವು ಕರೆನ್ಸಿಗಳಿಗೆ 3 — ಕೈಯಿಂದ ಬರೆದ ಶೇಕಡಾ ವಿಭಜನೆ ಸಾಮಾನ್ಯವಾಗಿ 2 ಅನ್ನು ಹಾರ್ಡ್-ಕೋಡ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಇತರ ಕರೆನ್ಸಿಗಳಿಗೆ ಮೌನವಾಗಿ ಮುರಿಯುತ್ತದೆ; ನಿಖರ-ಹಂಚಿಕೆ ದಿನಚರಿ ಘಾತವನ್ನು ಕರೆನ್ಸಿಯಿಂದಲೇ ಓದುತ್ತದೆ (ISO 4217).
- **ಈಗಾಗಲೇ ಹಂಚಿದ ಶೇಷವನ್ನು ಮರು-ಹಂಚಿಕೆ**: ಹಿಂದಿನ ಹಂಚಿಕೆಯ ಉಳಿದದ್ದರ ಮೇಲೆ ಅಚರತೆ ಪರಿಶೀಲನೆಗಳಿಲ್ಲದೆ ಹಂಚಿಕೆ ದಿನಚರಿಯನ್ನು ಮತ್ತೆ ನಡೆಸುವುದು, ಇದು ಅದೇ ಸೆಂಟ್ ಅನ್ನು ಅದೇ ಸ್ವೀಕರಿಸುವವರಿಗೆ ದ್ವಿಗುಣ ಜಮಾ ಮಾಡಬಹುದು.

## ಮೂಲಗಳು

- Fowler M. "Patterns of Enterprise Application Architecture." Addison-Wesley, 2002 — the `Money` and `Allocate` patterns.
- ISO 4217 — currency and funds code standard, which defines each currency's minor-unit exponent.
