# अचूक-पैसे खर्च वाटप

एकूण रकमेची — सामायिक अनुदान, पायाभूत सुविधा बिल, अंदाजपत्रक-प्रभाव आकडा — अनेक प्राप्तकर्त्यांमध्ये भोळ्या टक्केवारी अंकगणिताने विभागणी केल्यास नेहमीच असे भाग निर्माण होतात जे मूळ एकूणाशी परत जुळत नाहीत. अचूक-पैसे वाटप हा उपाय आहे: किमान चलन एककांमध्ये (सेंट) काम करणारी पूर्णांक/दशांश पद्धत, जी कितीही असमान विभागणी झाली तरी भाग *अगदी* पूर्णाइतकेच बेरीज होण्याची हमी देते. विभागलेल्या एकूणाला सेंटपर्यंत जुळवावे लागणाऱ्या कोणत्याही सॉफ्टवेअर अभियंत्याला — वेतन, अनुदान वितरण, सामायिक-सेवा चार्जबॅक — हा नमुना हवा, फ्लोटिंग-पॉइंट टक्केवारी नाही.

## हे का महत्त्वाचे आहे

एंटरप्राइझ सॉफ्टवेअर अभियांत्रिकीतील हा नामांकित, मूलभूत नमुना आहे: Martin Fowler यांचे *Patterns of Enterprise Application Architecture* (2002) `Money` आणि `Allocate` दस्तऐवजीकृत करते, कारण "$100 तीन भागांत विभागा" ही समस्या भोळा कोड सतत चुकवतो, आणि शांतपणे चुकवतो — कोणीतरी हिशेब जुळवतो आणि भाग एकूणापेक्षा एक सेंट कमी (किंवा जास्त) आढळतो तेव्हाच त्रुटी समोर येते. आरोग्य-अर्थशास्त्र आणि NHS वित्त कामात हे सैद्धांतिक नाही: अंदाजपत्रक-प्रभाव एकूण रकमा स्थळे, वर्षे किंवा संचालनालयांमध्ये विभागल्या जातात; सामायिक पायाभूत सुविधा आणि परवाना खर्च कर्मचारी संख्या किंवा क्रियाकलाप वाट्यानुसार विभागांमध्ये वाटले जातात. प्रत्येक विभागणी अचूक जुळली पाहिजे, कारण एकूणाशी न जुळणारे भाग हाती दिलेला वित्त संचालक संपूर्ण मॉडेलवरचा विश्वास गमावतो.

## गणित

```
Naive (broken) method:
  part_i = round(total × share_i / Σ shares)     — rounds each part independently

Exact method (largest remainder / "largest remainder allocation"):
  1. base_i = floor(total_minor_units × share_i / Σ shares)   — whole minor units (cents) only
  2. remainder = total_minor_units − Σ base_i                  — leftover cents, always < number of recipients
  3. distribute 1 extra minor unit each to the `remainder` recipients with the
     largest fractional remainder from step 1, until the leftover is exhausted

Result: Σ part_i == total, always, by construction.
```

अचूक पद्धत कोणताही भाग एकट्याने पूर्णांकित करत नाही — ती *संपूर्ण वाटप* एकाच क्रियेत पूर्णांकित करते, ज्यामुळे बेरीज अचल टिकते.

## सोडवलेले उदाहरण

$100.00 तीन समान भागांत विभागा (`shares = [1, 1, 1]`).

भोळी पद्धत: $100.00 ÷ 3 = $33.333…, स्वतंत्रपणे जवळच्या सेंटपर्यंत पूर्णांकित केल्यास प्रत्येक प्राप्तकर्त्याला $33.33. बेरीज: $33.33 × 3 = $99.99 — एक सेंट नाहीसा झाला, आणि तपासणीत पकडण्याइतकी कोणतीही एकल ओळ पुरेशी "चुकीची" नाही.

अचूक पद्धत: तिघांसाठी `base` = $33.33 (`floor(10,000 / 3) = 3,333` सेंट प्रत्येकी, एकूण 9,999 किमान एकके), 1 सेंट शिल्लक (10,000 − 9,999). तो एकमेव उरलेला सेंट भागाकारात सर्वात मोठा अपूर्णांक शेष असलेल्या प्राप्तकर्त्याला जातो — विशिष्ट प्राप्तकर्ता हा अंतर्गत टाय-ब्रेकचा तपशील आहे, कॉलरने त्यावर अवलंबून राहू नये. दोन प्राप्तकर्त्यांना $33.33 आणि एकाला $33.34 मिळतात, आणि तिन्ही भागांची बेरीज अगदी $100.00 होते.

एकूण अंदाजपत्रक-प्रभाव आकडा स्थळे, कोहॉर्ट किंवा आर्थिक वर्षांमध्ये विभागून प्रकाशित एकूणाशी जुळवावा लागतो तेव्हा [अंदाजपत्रक प्रभाव विश्लेषण](../अंदाजपत्रक-प्रभाव-विश्लेषण/) ला नेमके हेच अंकगणित हवे — अशा अनेक ओळींची भरकटीशिवाय बेरीज करण्याच्या सहचर समस्येसाठी [चलन-सुरक्षित खर्च एकत्रीकरण](../चलन-सुरक्षित-खर्च-एकत्रीकरण/) पहा.

## सॉफ्टवेअर अभियांत्रिकीशी संबंध

हा शब्दशः एंटरप्राइझ सॉफ्टवेअर आर्किटेक्चरमधील "Money पॅटर्न" आहे — नेमक्या याच बग श्रेणीसाठीचा मूलभूत, नामांकित नमुना, एकवेळची युक्ती नाही. `f64` मध्ये मोजलेल्या, प्रति-प्राप्तकर्ता पूर्णांकित केलेल्या आणि मूळ एकूणाशी कधीही न तपासलेल्या टक्केवारी विभागण्यांमधून याच बग श्रेणीमुळे खऱ्या आर्थिक-जुळवणी अपयशांनी उत्पादन गाठले आहे. हे या रेपॉझिटरीच्या [मालकीचा एकूण खर्च](../मालकीचा-एकूण-खर्च/) मॉड्यूलशी थेट जोडलेले आहे, जे सध्या वर्षे आणि पर्यायांमध्ये साधे फ्लोटिंग-पॉइंट खर्च जोडते — TCO किंवा अंदाजपत्रक-प्रभाव एकूण केवळ बेरीज न करता वाटावा लागतो तेव्हा तीच अचूकता शिस्त लागू होते.

## सामान्य चुका

- **सर्वात-मोठा-शेष ऐवजी टक्केवारी-मग-पूर्णांकन**: फ्लोटिंग-पॉइंट टक्केवारीने वाटप आणि प्रत्येक प्राप्तकर्त्याचे स्वतंत्र पूर्णांकन, जे पूर्णांकन त्रुटी वाढवते आणि क्वचितच एकूणाशी परत जुळते, विशेषतः अनेक प्राप्तकर्त्यांत.
- **चलन किमान-एकक घातांकांकडे दुर्लक्ष**: प्रत्येक चलनाला 2 दशांश स्थाने असतात असे गृहीत धरणे — जपानी येनला 0, काही चलनांना 3 — हाताने बनवलेली टक्केवारी विभागणी सहसा 2 कठोरपणे कोड करते आणि इतर चलनांसाठी शांतपणे मोडते; अचूक-वाटप रूटीन घातांक चलनातूनच वाचते (ISO 4217).
- **आधीच वाटलेल्या शेषाचे पुन्हा वाटप**: मागील वाटपातून उरलेल्यावर idempotency तपासण्यांशिवाय वाटप रूटीन पुन्हा चालवणे, ज्यामुळे त्याच प्राप्तकर्त्याला तोच सेंट दोनदा जमा होऊ शकतो.

## स्रोत

- Fowler M. "Patterns of Enterprise Application Architecture." Addison-Wesley, 2002 — the `Money` and `Allocate` patterns.
- ISO 4217 — currency and funds code standard, which defines each currency's minor-unit exponent.
