# מסגרת תקני הראיות של NICE (ESF)

ה-ESF היא מסגרת של NICE שמפרטת **כמה ראיות טכנולוגיית בריאות דיגיטלית צריכה, באופן יחסי לסיכון שלה**. זה הדבר הקרוב ביותר לתשובה רשמית ל"מה עלינו להוכיח לפני שה-NHS קונה את האפליקציה שלנו?"

## למה זה חשוב

ה-ESF (שוחררה לראשונה ב-2019, עודכנה ב-2022 לכסות בינה מלאכותית ואלגוריתמים אדפטיביים) מסווגת טכנולוגיות בריאות דיגיטליות לדרגות לפי תפקוד קליני, עם תקני ראיות **מצטברים** — 21 תקנים ב-5 קבוצות (גורמי עיצוב, ערך, ביצועים/יעילות, השפעה כלכלית, פריסה):

```
Tier A — system services, no direct patient outcome (e.g., e-rostering)
         → basic standards: credibility, data protection, technical assurance
Tier B — inform, simple monitoring, communication (e.g., symptom diary)
         → + evidence of user benefit, appropriate reliability
Tier C — treat, diagnose, or actively guide clinical management
         → + high-quality comparative effectiveness evidence (ideally RCT)
           and economic analysis
```

לראיות כלכליות, [ניתוח עלות-השלכות](../ניתוח-עלות-השלכות/) מקובל ברוב הדרגות; [ניתוח עלות-תועלתנות](../ניתוח-עלות-תועלתנות/) צפוי בסיכון הגבוה ביותר. ה-ESF מגדירה את **עלות הראיות שלכם לכניסה לשוק** — תקצבו אותה כמו כל עלות בנייה אחרת.

## המתמטיקה

אין נוסחאות — טבלת החלטה. החישוב הפעיל הוא מסחרי:

```
Evidence investment required = f(tier)
  Tier A: documentation + assurance ≈ £10k–50k
  Tier B: observational/comparative user-benefit study ≈ £50k–250k
  Tier C: RCT-grade comparative study + economic model ≈ £250k–£2M+

Position your product's claims deliberately: claiming "supports clinical
decisions" instead of "informs patients" moves you a tier and can 10× the bill.
```

## דוגמה מחושבת

יצרנית אפליקציית תזכורות לתרופות שוקלת להוסיף תכונת המלצה להתאמת מינון.

- כאפליקציית תזכורות: **דרגה B** — מחקר קוהורטה שמראה שיפור היענות מספיק.
- עם המלצות מינון: **דרגה C** — ראיות ליעילות השוואתית (כנראה RCT מול טיפול רגיל) בתוספת ניתוח כלכלי.

אם ה-RCT עולה £600k וההכנסה המצטברת של תכונת המינון היא £200k בשנה, התכונה צריכה להחזיק ערך 3+ שנים לפני שעלויות הראיות מתאזנות — החלטת מוצר שנראית שונה לגמרי כשמתמחרים את דרגת ה-ESF. צוותים רבים שולחים את מוצר דרגה B ומשהים את טענת דרגה C עד למימון.

## הקשר להנדסת תוכנה

ה-ESF היא תבנית הממשל הניתנת להעברה ביותר במאגר הזה: **דרישות ראיות מדורגות-סיכון לאימוץ כלים**. גרסה פנימית: מעצב קוד צריך הדגמה (דרגה A); כלי פריון שטוען לחיסכון בשעות צריך פיילוט מדוד (דרגה B); שער בינה מלאכותית שחוסם פריסות אוטומטית או כותב קוד קליני אוטומטית צריך ראיות ברמת ניסוי מבוקר לפני פריסה ארגונית (דרגה C). ראיות יחסיות עוצרות את שני מצבי הכשל — בירוקרטיה שחונקת כלים טריוויאליים, ותחושות שמשלחות כלים משמעותיים. ראו גם [המסלול המהיר DiGA](../המסלול-המהיר-diga-של-גרמניה/) למשלים "אימוץ זמני עם מועד אחרון לראיות".

## מלכודות נפוצות

- **סיווג שגוי של דרגה מתוך משאלת לב** — רגולטורים וקונים מסווגים לפי מה שהמוצר *עושה*, לא מה שהשיווק אומר.
- **ראיות שנבנות אחרי המוצר**: התקנת RCT בדיעבד על מוצר שנשלח בלי מדידה או equipoise היא איטית ולעיתים קרובות בלתי אפשרית.
- **עמידה ב-ESF ושכחת השאר**: ה-ESF יושבת לצד DTAC (בטיחות קלינית, הגנת נתונים, יכולת פעולה הדדית) ולבינה מלאכותית, אישור רגולטורי — ראו [הערכה רגולטורית של בינה מלאכותית](../הערכה-רגולטורית-של-בינה-מלאכותית/).
