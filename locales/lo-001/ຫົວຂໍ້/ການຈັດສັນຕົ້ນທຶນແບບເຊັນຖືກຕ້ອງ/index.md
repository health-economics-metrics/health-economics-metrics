# ການຈັດສັນຕົ້ນທຶນແບບເຊັນຖືກຕ້ອງ

ການແບ່ງຈຳນວນເງິນທັງໝົດ — ເງິນຊ່ວຍເຫຼືອຮ່ວມ, ໃບບິນໂຄງສ້າງພື້ນຖານ, ຕົວເລກຜົນກະທົບຕໍ່ງົບປະມານ — ໃຫ້ຜູ້ຮັບຫຼາຍຄົນດ້ວຍເລກເປີເຊັນແບບງ່າຍໆ ມັກໃຫ້ສ່ວນຕ່າງໆທີ່ລວມກັບຄືນບໍ່ຕົງຍອດເດີມ. ການຈັດສັນແບບເຊັນຖືກຕ້ອງແມ່ນການແກ້ໄຂ: ວິທີເລກຖ້ວນ/ທົດສະນິຍົມ ທີ່ເຮັດວຽກໃນຫົວໜ່ວຍເງິນຍ່ອຍ (ເຊັນ) ຮັບປະກັນວ່າສ່ວນຕ່າງໆລວມ*ຕົງ*ກັບທັງໝົດ ບໍ່ວ່າຈະຫານບໍ່ເທົ່າກັນປານໃດ. ວິສະວະກອນຊອບແວຄົນໃດທີ່ຕ້ອງກະທົບຍອດການແບ່ງຮອດເຊັນ — ເງິນເດືອນ, ການຈ່າຍເງິນຊ່ວຍເຫຼືອ, ການຮຽກເກັບບໍລິການຮ່ວມ — ຕ້ອງການແບບແຜນນີ້ ບໍ່ແມ່ນເປີເຊັນຈຸດລອຍ.

## ເປັນຫຍັງຈຶ່ງສຳຄັນ

ນີ້ແມ່ນແບບແຜນພື້ນຖານທີ່ມີຊື່ໃນວິສະວະກຳຊອບແວວິສາຫະກິດ: *Patterns of Enterprise Application Architecture* (2002) ຂອງ Martin Fowler ບັນທຶກ `Money` ແລະ `Allocate` ກໍຍ້ອນ "ແບ່ງ $100 ເປັນສາມສ່ວນ" ແມ່ນບັນຫາທີ່ໂຄດແບບງ່າຍເຮັດຜິດຢູ່ສະເໝີ ແລະ ຜິດແບບງຽບໆ — ຂໍ້ຜິດພາດປະກົດສະເພາະເມື່ອມີຄົນກະທົບຍອດບັນຊີແລ້ວພົບວ່າສ່ວນຕ່າງໆຂາດ (ຫຼືເກີນ) ໜຶ່ງເຊັນ. ໃນວຽກເສດຖະສາດສຸຂະພາບແລະການເງິນ NHS ນີ້ບໍ່ແມ່ນທິດສະດີ: ຍອດລວມຜົນກະທົບຕໍ່ງົບປະມານຖືກແບ່ງຂ້າມສະຖານທີ່, ປີ, ຫຼື ສຳນັກ; ຕົ້ນທຶນໂຄງສ້າງພື້ນຖານແລະໃບອະນຸຍາດຮ່ວມຖືກແບ່ງໃຫ້ພະແນກຕາມຈຳນວນພະນັກງານຫຼືສັດສ່ວນກິດຈະກຳ. ທຸກການແບ່ງຕ້ອງກະທົບຍອດຢ່າງແນ່ນອນ ເພາະຜູ້ອຳນວຍການການເງິນທີ່ໄດ້ຮັບສ່ວນຕ່າງໆທີ່ລວມບໍ່ຕົງຍອດຈະເລີກໄວ້ວາງໃຈແບບຈຳລອງທັງໝົດ.

## ຄະນິດສາດ

```
Naive (broken) method:
  part_i = round(total × share_i / Σ shares)     — rounds each part independently

Exact method (largest remainder / "largest remainder allocation"):
  1. base_i = floor(total_minor_units × share_i / Σ shares)   — whole minor units (cents) only
  2. remainder = total_minor_units − Σ base_i                  — leftover cents, always < number of recipients
  3. distribute 1 extra minor unit each to the `remainder` recipients with the
     largest fractional remainder from step 1, until the leftover is exhausted

Result: Σ part_i == total, always, by construction.
```

ວິທີທີ່ແນ່ນອນບໍ່ເຄີຍປັດສ່ວນໃດສ່ວນໜຶ່ງແຍກຕ່າງຫາກ — ມັນປັດ*ການຈັດສັນທັງໝົດ*ເປັນການດຳເນີນງານດຽວ ເຊິ່ງເຮັດໃຫ້ຄຸນສົມບັດຄົງທີ່ຂອງຜົນລວມຍັງຄົງ.

## ຕົວຢ່າງການຄິດໄລ່

ແບ່ງ $100.00 ເປັນສາມສ່ວນເທົ່າກັນ (`shares = [1, 1, 1]`).

ວິທີແບບງ່າຍ: $100.00 ÷ 3 = $33.333… ປັດແຍກເປັນເຊັນທີ່ໃກ້ທີ່ສຸດໃຫ້ $33.33 ສຳລັບແຕ່ລະຜູ້ຮັບ. ລວມ: $33.33 × 3 = $99.99 — ໜຶ່ງເຊັນຫາຍໄປ ແລະ ບໍ່ມີລາຍການດຽວທີ່ "ຜິດ" ພໍທີ່ຈະສັງເກດເຫັນດ້ວຍການກວດ.

ວິທີແນ່ນອນ: `base` = $33.33 ສຳລັບທັງສາມ (ລວມ 9,999 ຫົວໜ່ວຍຍ່ອຍຈາກ `floor(10,000 / 3) = 3,333` ເຊັນຕໍ່ຄົນ) ເຫຼືອເສດ 1 ເຊັນ (10,000 − 9,999). ເຊັນທີ່ເຫຼືອນັ້ນໄປຫາຜູ້ຮັບທີ່ມີເສດສ່ວນທີ່ໃຫຍ່ທີ່ສຸດໃນການຫານ — ຜູ້ຮັບສະເພາະແມ່ນລາຍລະອຽດການຕັດສິນເສມີພາຍໃນ ບໍ່ແມ່ນສິ່ງທີ່ຜູ້ເອີ້ນຄວນອາໄສ. ສອງຜູ້ຮັບໄດ້ $33.33 ແລະ ໜຶ່ງຄົນໄດ້ $33.34 ແລະ ສາມສ່ວນລວມ $100.00 ພໍດີ.

ນີ້ແມ່ນເລກຄະນິດທີ່[ການວິເຄາະຜົນກະທົບຕໍ່ງົບປະມານ](../ການວິເຄາະຜົນກະທົບຕໍ່ງົບປະມານ/)ຕ້ອງການທຸກຄັ້ງທີ່ຍອດລວມຜົນກະທົບຕໍ່ງົບປະມານຕ້ອງຖືກແບ່ງຂ້າມສະຖານທີ່, ກຸ່ມ, ຫຼື ປີການເງິນແລະກະທົບຍອດກັບຄືນຍອດລວມທີ່ເຜີຍແຜ່ — ເບິ່ງ[ການລວມຕົ້ນທຶນທີ່ປອດໄພດ້ານສະກຸນເງິນ](../ການລວມຕົ້ນທຶນທີ່ປອດໄພດ້ານສະກຸນເງິນ/) ສຳລັບບັນຫາຄູ່ຂອງການລວມລາຍການດັ່ງກ່າວຫຼາຍອັນໂດຍບໍ່ເລື່ອນ.

## ຄວາມເຊື່ອມໂຍງກັບວິສະວະກຳຊອບແວ

ນີ້ແມ່ນ "ແບບແຜນ Money" ຈາກສະຖາປັດຕະຍະກຳຊອບແວວິສາຫະກິດແທ້ໆ — ແບບແຜນພື້ນຖານທີ່ມີຊື່ສຳລັບຊັ້ນບັກນີ້ ບໍ່ແມ່ນກົນລະຍຸດຄັ້ງດຽວ. ຄວາມລົ້ມເຫຼວຂອງການກະທົບຍອດທາງການເງິນທີ່ແທ້ຈິງຖືກສົ່ງມອບຈາກບັກຊັ້ນນີ້ແນ່ນອນ: ການແບ່ງເປີເຊັນທີ່ຄຳນວນໃນ `f64`, ປັດຕໍ່ຜູ້ຮັບ, ແລະ ບໍ່ເຄີຍກວດກັບຍອດເດີມ. ມັນເຊື່ອມໂດຍກົງກັບໂມດູນ[ຕົ້ນທຶນການເປັນເຈົ້າຂອງທັງໝົດ](../ຕົ້ນທຶນການເປັນເຈົ້າຂອງທັງໝົດ/)ຂອງຄັງນີ້ ເຊິ່ງປັດຈຸບັນລວມຕົ້ນທຶນຈຸດລອຍທຳມະດາຂ້າມປີແລະທາງເລືອກ — ລະບຽບວິໄນຄວາມແນ່ນອນດຽວກັນນຳໃຊ້ທຸກຄັ້ງທີ່ຍອດລວມ TCO ຫຼືຜົນກະທົບຕໍ່ງົບປະມານຕ້ອງຖືກແບ່ງ ບໍ່ແມ່ນພຽງລວມ.

## ຂໍ້ຜິດພາດທີ່ພົບເລື້ອຍ

- **ເປີເຊັນແລ້ວປັດ ແທນທີ່ຈະເປັນ largest-remainder**: ຈັດສັນດ້ວຍເປີເຊັນຈຸດລອຍແລ້ວປັດແຕ່ລະຜູ້ຮັບແຍກກັນ ເຊິ່ງທະວີຄວາມຜິດພາດການປັດແລະຫາຍາກທີ່ຈະລວມກັບຄືນຍອດ ໂດຍສະເພາະຂ້າມຜູ້ຮັບຫຼາຍຄົນ.
- **ລະເລີຍເລກກຳລັງຫົວໜ່ວຍຍ່ອຍຂອງສະກຸນເງິນ**: ສົມມຸດວ່າທຸກສະກຸນເງິນມີ 2 ຕຳແໜ່ງທົດສະນິຍົມ — ເຢນຍີ່ປຸ່ນມີ 0, ບາງສະກຸນມີ 3 — ການແບ່ງເປີເຊັນທີ່ຂຽນເອງມັກຝັງ 2 ແລະ ພັງໃນສະກຸນອື່ນແບບງຽບໆ; ໂປຣແກຣມຈັດສັນແນ່ນອນອ່ານເລກກຳລັງຈາກສະກຸນເງິນເອງ (ISO 4217).
- **ຈັດສັນເສດທີ່ຈັດສັນແລ້ວຄືນ**: ດຳເນີນໂປຣແກຣມຈັດສັນຊ້ຳກັບສິ່ງທີ່ເຫຼືອຈາກການຈັດສັນກ່ອນໂດຍບໍ່ມີການກວດ idempotency ເຊິ່ງອາດໃຫ້ເຊັນດຽວກັນສອງເທື່ອກັບຜູ້ຮັບດຽວກັນ.
